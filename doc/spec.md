# quickchart 設計

本書は `doc/requirement.md` を入力として、MVPの実装方針を定める。要求仕様の「9. 今後の検討事項」に列挙された未決事項は、本章で全て解決する(解決結果は「12. オープンクエスチョンへの回答」に一覧化)。

## 1. アーキテクチャ概要

- Tauri (Rust) をバックエンド、React + TypeScript をフロントエンドとするデスクトップアプリケーション。
- 図形描画はフロントエンド側で SVG を DOM として直接操作する(仮想的な canvas ライブラリは使わず、Shape モデル→React コンポーネント→SVG 要素、という素直な描画パイプラインにする)。
- Rust バックエンドは「ファイル I/O」「PNG/EMF へのラスタライズ・ベクター変換」「クリップボード操作」など OS 依存処理に責務を限定する。図形の編集ロジック・Undo/Redo・構造化テンプレート生成はすべてフロントエンド(TypeScript)側に置く。理由: これらはビジネスロジックであり、Rust/TS 間の IPC 往復を頻発させると操作のレスポンスが悪化するため。

## 3. データモデル

### 3.1 Shape (共通)

```ts
type ShapeId = string; // uuid v4

interface ShapeBase {
  id: ShapeId;
  type: "rect" | "ellipse" | "line" | "arrow" | "connector" | "text";
  x: number; y: number;           // 左上座標(キャンバス座標系)
  width: number; height: number;
  rotation: number;               // 度
  style: ShapeStyle;
  groupId?: string;               // グルーピング先
  zIndex: number;                 // レイヤー順序
  templateNodeIds?: string[];     // 構造化テンプレート由来の場合、対応する階層テキストノードのID群(通常1件。ベン図で複数集合が同一要素を共有する場合のみ複数件)
}

interface ConnectorShape extends ShapeBase {
  type: "connector" | "arrow";
  fromShapeId?: ShapeId; fromAnchor?: AnchorPoint; // 図形に接続している場合
  toShapeId?: ShapeId;   toAnchor?: AnchorPoint;
  points: Point[];                // 未接続端点、または経路の中間点
}

interface TextShape extends ShapeBase {
  type: "text";
  content: string;
  align: "left" | "center" | "right";
  bulletMarker?: string;          // 表示専用の "• "/"- " 等のプレフィックス(§6.2.3/§6.2.4、content 自体には含めない)
}

// 任意の閉多角形(ピラミッド図のピラミッド段 - §6.2.5)。points は絶対座標ではなく
// 自身の x/y/width/height に対する 0〜1 の比率で持つ。これにより移動・リサイズは
// 既存の汎用ロジック(x/y/width/height のみを操作する computeAnchoredResize 等)が
// そのまま使え、図形種別ごとのリサイズ処理を追加する必要がない。
interface PolygonShape extends ShapeBase {
  type: "polygon";
  points: Point[];
}
```

### 3.2 Document

```ts
interface Layer { id: string; name: string; visible: boolean; locked: boolean; shapeIds: ShapeId[]; }

interface OutlineNode {
  id: string;                     // nodeId(uuid v4)。構造化編集操作(追加/字下げ等)で採番され、テキスト編集では不変
  text: string;
  children: OutlineNode[];
}

interface StructuredBlock {
  id: string;
  pattern: "pyramid" | "logicTree" | "matrix" | "venn" | "headingBullets" | "bulletMatrix" | "pyramidChart";
  outline: OutlineNode[];         // 階層テキストの構造化データ(ソース・オブ・トゥルース)。ルートは複数可
  params: Record<string, unknown>;// パターン別パラメータ(象限数、集合数など)
  generatedShapeIds: ShapeId[];   // このブロックが生成した図形(直接編集も可)
}

interface Document {
  formatVersion: number;          // プロジェクトファイルのスキーマバージョン
  shapes: Record<ShapeId, Shape>;
  layers: Layer[];
  structuredBlocks: StructuredBlock[];
  colorThemeId: string;
}
```

### 3.3 プロジェクトファイル形式

- 拡張子 `.qct`。内容は上記 `Document` を JSON にシリアライズしたものを正とする。
- 要求仕様 4.6 は「JSON+SVGベースなど」と例示しているが、実際の保存形式は **JSON のみ** とし、SVG はプロジェクトファイルに保持しない。表示・エクスポート用の SVG はいつでも `Document` から再生成できるため、二重管理による不整合を避ける。エクスポート(4.5)は別ファイルへの書き出しという位置付けなので、この方針は要求仕様と矛盾しない。
- `formatVersion` を先頭に持たせ、将来のスキーマ変更に備えたマイグレーション関数(`migrateDocument(doc, fromVersion)`)を `projectFile.ts` に用意する。

### 3.4 ユーザーテンプレート

要求仕様 4.4「よく使う図形の組み合わせをユーザー自身がテンプレート登録できる」に対応するデータモデル。プロジェクトファイルではなく、プロジェクトを跨いで再利用するためアプリ設定ディレクトリ側に保存する(詳細は §6.4)。

```ts
interface UserTemplate {
  id: string;                     // uuid v4
  name: string;
  shapes: Shape[];                // 選択図形群のスナップショット。バウンディングボックス左上を原点(0,0)に正規化した相対座標で保持
  createdAt: string;              // ISO 8601
}
```

## 4. 状態管理・Undo/Redo

- 状態管理には **Zustand** を採用する(Redux 比でボイラープレートが少なく、TypeScript との親和性が高いため)。
- `documentStore` は Immer ミドルウェアを介して更新する。Undo/Redo は Immer の `produceWithPatches` が返す `patches`/`inversePatches` を操作ごとにスタックへ積む方式で実装する(`historyMiddleware.ts`)。
  - 構造化テンプレートの再生成(アウトライン編集による図形の一括追加/削除)も 1 回の操作として 1 セットの patch にまとめ、Undo で一括して戻せるようにする。
- `selectionStore` は Undo/Redo の対象外(選択状態は履歴に含めない)。

## 5. キャンバス・図形操作(自由配置)

- 選択・リサイズ・回転ハンドルの実装には **react-moveable** を使う。SVG 要素(`rect`/`ellipse`/`g` など)を直接対象にでき、要求仕様の「SVGをDOMとして直接操作する」方針と合致する。
- 整列・分布・グリッドスナップは `core/layout/align.ts` / `snap.ts` に純関数として実装し、UI から独立してユニットテスト可能にする。
- コネクタの追従: 接続先図形の `x/y/width/height/rotation` の変更を購読し、`fromAnchor`/`toAnchor` の絶対座標を再計算して経路を再描画する。MVP では直線接続のみとし、直交ルーティング(カギ線)は将来対応とする。
- グルーピングは `groupId` の付与のみで表現し、専用のグループ図形は作らない(選択・移動・スタイル変更をまとめて行う際に `groupId` でフィルタする)。

### 5.1 ツールパネル: アイコン + コマンドパレット

要求仕様 4.1「選択ツール・基本図形ツールの切り替えUIは、名前付きボタンの列挙ではなくアイコンボタン+コマンドパレットで構成」に対応する。対象は選択ツールと基本図形ツール(矩形・楕円・直線・テキスト・コネクタ・矢印)の計7件で、MVP では他のコマンド(整列・グルーピング等、いずれもショートカットキーか右パネルの通常ボタンで既に到達可能)まではコマンドパレットの検索対象に含めない(要求仕様9章オープンクエスチョンへの回答)。

- **アイコン**: 新規ライブラリは導入せず、`ToolPanel.tsx` 内に手書きのインライン SVG アイコン(線画・最小限のパス)を用意する。7個程度であれば、`lucide-react` 等のアイコンライブラリを依存に追加するコストの方が高いと判断。図形そのものの描画(`ShapeRenderer.tsx`)と統一感のある、線のみのシンプルな見た目にする。
- **`ToolPanel.tsx` の変更**: 現行の「アイコン無し・ラベル付きボタンを縦に並べる」実装を、アイコンのみの正方形ボタンを横並び(1〜2行)にしたコンパクトな配置に変更する。各ボタンは `title` 属性でラベル(例:「矩形」)をネイティブツールチップとして表示する(削除ボタンの `×` 等、本アプリの他アイコン的ボタンと同じ方式)。選択中のツールのハイライト表示(`tool-button-active` 相当のスタイル)は現状を踏襲する。
- **`CommandPalette.tsx`(新規)**: 画面中央にオーバーレイ表示するモーダル。
  - **呼び出し**: `Ctrl+K`(Mac は `Cmd+K`)のグローバルショートカット、および `ToolPanel.tsx` に追加する検索アイコンボタンのクリック。ショートカットは `App.tsx` の既存 `handleKeyDown`(Undo/Redo 等と同じ場所)に追加する。
  - **一覧・絞り込み**: `ToolPanel.tsx` の7件(id/label/icon)をそのままデータソースとして再利用し(一覧を二重管理しない)、入力欄の文字列でラベルへの大小文字区別なし部分一致フィルタを行う。7件程度の規模のため、あいまい検索等の高度なマッチングは導入しない。
  - **キーボード操作**: 入力欄はモーダルを開いた時点で自動フォーカスする。`↑`/`↓` で候補選択を移動、`Enter` で確定、`Escape` で閉じる。これらは(`StructuredTextPanel.tsx` の行内入力の `Tab`/`Enter` 処理と同様)入力欄自身の `onKeyDown` で処理し、`App.tsx` 側のグローバルハンドラ(テキスト入力中はショートカットを無視する既存ガードがあるため)には依存しない。候補のクリック確定にも対応する。
  - **確定時の挙動**: 選択したツールを `activeTool` に反映し(`ToolPanel.tsx` のアイコンボタンと同じ `onSelectTool` コールバックを共有)、パレットを閉じる。
  - **状態管理**: パレットの開閉・検索文字列は `App.tsx` のローカル state(`activeTool`/`pendingUserTemplate` と同じ持ち方)とする。他コンポーネントから参照される共有状態ではないため、専用の Zustand ストアは設けない。

## 6. 構造化テンプレート生成

### 6.1 階層テキストの記法・編集方式

Markdown の箇条書きに近い、インデント+ハイフンのアウトライン記法を見た目のメンタルモデルとして採用する(独自記法・JSON直接編集は不採用)。理由: 対象ユーザー(コンサルタント等)が Markdown/Word/PowerPoint のアウトライン表示に日常的に触れており学習コストが低いこと、将来的に他ツールとのテキストのコピペ互換性を確保しやすいこと。

```
- 親項目
  - 子項目1
  - 子項目2
    - 孫項目
- 親項目2
```

**編集UIは素のテキストエリアではなく、行単位の入力欄を持つ構造化アウトラインエディタとする**(`StructuredTextPanel.tsx`)。各行が独立した入力欄で、Tab/Shift+Tab で字下げ・字上げ、行ごとのボタン操作で兄弟/子ノードの追加・削除・並べ替えを行う(Word/PowerPointのアウトラインビューに近い操作感)。

- 理由: `StructuredBlock.outline`(§3.2 の `OutlineNode[]`)が同期のソース・オブ・トゥルースであり、`nodeId` は「行の内容」ではなく「どの操作で生成されたか」に紐づく。素のテキストを自由に書き換えられる方式だと、再パース時に「既存行の内容が変わった」のか「行が削除されて別の行が追加された」のかを区別する決定的な方法がなく、双方向同期(§6.3)が成立しない。行単位の明示的な操作(追加/削除/字下げ)であれば `nodeId` の生成・破棄が一意に決まる。
- 外部テキストからの一括貼り付け(Word/PowerPoint のアウトラインからのコピペ等、当初の記法選定理由に対応)は「インポート」操作として提供する。貼り付けられた複数行テキストは `outlineParser.ts` でパースし、そのブロックの既存 `outline` を丸ごと置き換えて全ノードに新規 `nodeId` を採番する(=このケースのみ既存の生成図形は破棄・再生成される。Undo 可能なため確認ダイアログは出さない)。
- インデント単位はスペース2つ、またはタブ1つ(パース時にタブはスペース2つに正規化)。`- ` で始まらない行・空行は無視する。
- 逆に `OutlineNode[]` からテキスト表現へのシリアライズ(コピー用のエクスポート等)は `outlineSerializer.ts` が担う。

| フロー図（横型） | 下記 6.2.8 |
| フロースケジュール（縦） | 下記 6.2.9 |

「ピラミッドストラクチャー」(UI上の表示名は「ツリー図」)と「ロジックツリー」は、親子関係を示す接続線(エルボー型。ツリー図: 親の下辺中央から下に伸び、子たちの中心を結ぶ横線("バス")を経て各子の上辺中央へ下りる。ロジックツリーはこれを90度回転させたもので、親の右辺中央から右に伸び、子たちの中心を結ぶ縦のバスを経て各子の左辺中央へ入る)を薄いグレー(テーマに依存しない固定色、`style.ts` の `treeConnectorStyle`)で描画する。バスの位置は、親の辺と(最も近い)子の辺のちょうど中間(2本のスタブが等しい長さになる位置)に置く固定オフセットではなく都度計算する。子が1つだけの場合はバス部分を省略し、スタブ2本だけになる。接続線は `templateNodeIds: []` の非追跡図形として扱い(箇条書きマトリクスのグリッド線と同じ扱い)、`StructuredBlock.params._treeConnectorShapeIds` で管理する。この2パターンは他パターンと異なり階層テキストの追加/削除を増分配置(`buildNodeShape`)で行うため、接続線は各ノードの**実際の現在位置**(`treeLayout.ts` の理想化されたカーソル配置ではなく、手動での位置調整結果も含む)から都度再計算し(`sync.ts` の `regenerateTreeConnectors`、方向は `treeConnectorDirection` がパターンから決める)、追加・削除・字下げ/字上げ・並べ替え・一括インポートのいずれの操作後にも呼び出す。他パターンには適用しない。ブロック間の距離は、増分配置(`sync.ts` の `newNodeOffset`)・`layoutTree` ベースの一括生成/再配置(`pyramid.ts`/`logicTree.ts` の `GAP`)のいずれも 36px(導入時の1.5倍)に統一してある。`newNodeOffset` は当初「基準図形からの合計オフセット」を固定値で返していたが、これだと基準図形の実サイズが既定の 160x60 から外れた場合(手動リサイズ、あるいは値そのものが過去に変更された履歴が混在する等)に見た目の間隔が図形ごとにばらついてしまう(報告されたバグ:兄弟同士のはずの間隔が箇所によって大きく異なる)。そのため現在は「基準図形の実際の幅/高さ + 固定ギャップ36px」を都度計算する方式にしている。

#### 6.2.1 マトリクス(4象限)

- 階層テキストは最大2階層とする。**1階層目のノードは象限そのもの(4個を基本とし、不足分は空の象限として扱う)**、2階層目はその象限内の箇条書き項目。1階層目の出現順は自然な読み順である「左上→右上→左下→右下」の固定順で解釈する。
- マトリクスは4象限で固定のため、1階層目(ルート)が既に4件ある状態では `StructuredTextPanel.tsx` 上で「ルートを追加」操作自体を無効化し、5件目以降が生成されない矛盾状態を作らせない。あわせて `matrix.ts` 側でも防御的に5件目以降のルートを無視する(手編集・旧バージョンのプロジェクトファイル等、UI制約を経由しない入力に対するフォールバック)。
- 縦軸・横軸自体のラベル(例:「市場成長性」「市場シェア」)は、階層テキストでは表現しない。軸ラベルと象限の間に親子関係がなく、木構造に押し込むと構造が歪むため、`StructuredBlock.params`(テンプレートパラメータ、要求仕様 4.2 の「パラメータ調整」に対応)の専用フィールド(`axisXLabel` / `axisYLabel`)として `StructuredTextPanel.tsx` に別入力欄を設ける。MVPでは軸名2件のみとし、各軸の両端ラベル(4件)は実装コストに対して優先度が低いため見送る(`params` は汎用の `Record<string, unknown>` なので、必要になれば後から追加できる)。軸ラベルから生成される `TextShape` も(対応する `outline` ノードを持たないため `params._axisShapeIds` で追跡する)そのブロックの `generatedShapeIds` に含める。
- 例:
  ```
  - 高成長・高シェア
    - 項目A
    - 項目B
  - 低成長・高シェア
  - 高成長・低シェア
    - 項目C
  - 低成長・低シェア
    - 項目D
  ```

#### 6.2.2 ベン図

- 要求仕様 4.2 で「1階層目=集合名、2階層目=要素。複数集合に同一要素を記載すると重なり領域として扱う」と既に確定しているため、設計ではこれを実現するアルゴリズムのみを定める。
- 対応集合数は **2〜3** を MVP 対象とする(`params.setCount`)。4集合以上は円の重なりが複雑になり自動レイアウトの可読性が下がるため将来対応とし、必要な場合は自由配置キャンバス上で手動作図する。ルート(集合)ノードの追加・削除は `params.setCount` に連動させ、`StructuredTextPanel.tsx` 上で 2〜3 の範囲外になる操作は無効化する。
- アルゴリズム: 全要素について「所属する集合名の組み合わせ(冪集合のキー)」を、**要素のテキスト内容が完全一致するかどうか**で求め、同じ組み合わせを持つ要素をグループ化する。2集合/3集合それぞれについて円の配置(中心座標・半径)を固定パターンとして事前定義し、各組み合わせに対応する重なり領域の代表点(重心)をあらかじめ計算しておく。各グループの要素はその代表点を基準に縦に並べて配置する。
- 例: `集合A: りんご, みかん, ぶどう` / `集合B: みかん, ぶどう, もも` → 「みかん・ぶどう」は `{A,B}` の組み合わせとなり A∩B 領域に配置。
- **1図形=複数nodeIdの対応**: 上記のとおり、同一テキストの要素は集合ごとに別々の `OutlineNode`(別々の `nodeId`)として存在するが、生成される図形は1つにまとまる。そのため該当図形の `templateNodeIds` には複数の `nodeId` が入る(§3.1)。
- **所属集合の組み合わせが変化した場合の扱い**: ベン図は他パターンと異なり、図形の位置がテキスト内容(どの集合に属するか)に直接従属する特殊なパターンである。要素テキストの編集によって所属集合の組み合わせが変わった場合(例: 共有していた「みかん」の片方だけを書き換えて非共通語にする)、その要素は再グルーピングされ、影響を受ける図形は新しい重なり領域の代表点へ位置を再計算する(=このケースに限り手動で調整した位置は保持されない)。組み合わせが変化しないテキスト編集(§6.3 の通常ケース)では位置を変えない。

#### 6.2.3 見出し付き箇条書き

- 階層テキストは最大2階層とする。**1階層目のノードは行(表の1段)そのもので、左側の見出しセルとして描画される**。2階層目はその行の箇条書き項目で、見出しセルの右側に縦に並べて描画される。ルート数の上限はない。
- 各行は次の3種の図形から構成される(`headingBullets.ts`)。
  - **見出しセル**: 1階層目ノード1つにつき図形1つ。背景色(テーマの `primary[0]`)と白文字ラベルを同じ図形で兼ねる(マトリクスの象限のように背景とタイトルを別図形にしない理由: 見出しセルは行全体がそのままラベルであり、タイトル下に別途空けるべき「項目エリア」がないため)。行の高さは自身の箇条書き項目数から決まる(項目が多いほど行が高くなる)。
  - **箇条書き項目**: 2階層目ノード1つにつき図形1つ。枠なし・左揃えで、見出しセルの右側に項目数ぶん縦に並べる。表示上「• 」を項目テキストの前に付与するが、これは表示専用(`TextShape.bulletMarker`)であり、編集対象のテキスト本体(`content`)には含めない(§6.3 のテキスト編集がそのまま素のテキストを更新できるようにするため)。
  - **行区切り線**: 隣接する行の間にのみ破線を1本描画する(先頭行の上・末尾行の下には描かない)。対応する `OutlineNode` を持たないため `templateNodeIds` は空になる。
- マトリクス・ベン図と同様、行の高さは他の行の箇条書き項目数に依存しないが、後続の行のY座標は先行するすべての行の高さに依存するため、**箇条書きの追加・削除は影響を受ける行以降をすべて再レイアウトする**(`isFullyRelayoutedPattern` に該当、§6.3 の「通常はテキスト変更のみで位置は変えない」の対象外)。ただし項目の**テキストのみ**の編集は位置に影響しないため、他パターンと同じ通常の同期(内容のみ更新)で扱う。
- テキストの折り返しは行わない(他パターンと同じ制約)。見出し・項目とも1行分の固定高さで描画するため、長いテキストは図形の幅を超えて表示される可能性がある。

#### 6.2.4 箇条書きマトリクス

見出し付き箇条書き(§6.2.3)を列方向にも拡張し、行見出し×列見出しの各セルが「太字下線付きタイトル + その配下の詳細行」からなる2階層の箇条書きを持つ表。見出し付き箇条書きと異なり、通常の「インデント付き `- ` 箇条書き」テキストではなく、**Markdown(表 + 見出し + 箇条書き)を主な入力形式とする**(理由は後述)。

- **階層テキストは4階層**: 1階層目=行(見出し付き箇条書きの行と同じ役割)、2階層目=セル(列と位置で対応付け、テキスト自体は使わない)、3階層目=セル内のタイトル箇条書き(太字下線)、4階層目=そのタイトルの詳細行(通常の箇条書き)。
- **列見出しは階層テキストで表現しない**: マトリクスの軸ラベル(§6.2.1)と同じ理由で、列見出しは全行で共通のラベルであり木構造に押し込むと同じ文言を行ごとに重複入力させることになる。`StructuredBlock.params.columnHeaders`(`string[]`)に保持し、`StructuredTextPanel.tsx` に専用の可変長リスト入力(列の追加・削除・改名)を設ける。2階層目(セル)ノードはこの列配列と**位置(インデックス)で対応**し、そのノード自身の `text` は使われない(空文字のまま)。
- **Markdown入力形式**: 1階層目〜4階層目をインデント付き箇条書きで手入力するのは非実用的(特に列見出しの重複入力、太字/詳細の区別)なため、`bulletMatrixParser.ts` が下記の形の Markdown 文書を解析して `columnHeaders` と `outline` を一括生成する。「テキストで一括インポート」がこのパターンでは主な作成手段になる(既存パターンの一括インポートは補助的な位置づけだったのに対し、こちらは主経路)。
  ```
  | 行見出し列のラベル(未使用) | 列見出し1 | 列見出し2 |
  |---|---|---|
  | 行1の見出し | A1 | B1 |
  | 行2の見出し | A2 | B2 |

  ## 行1の見出し

  ### A1

  - **タイトル1**
    - 詳細1-1
    - 詳細1-2

  - **タイトル2**
    - 詳細2-1

  ### B1

  - **タイトル3**
    - 詳細3-1
  ```
  - 先頭のテーブルで行見出し・列見出し・各セルのプレースホルダID(`A1`/`B1`等、テーブル内でのみ使う識別子)を定義する。
  - `## <行見出しのテキスト>` でその行のセクションを開始し(テーブルの行見出しセルと完全一致で対応付け)、その中の `### <プレースホルダID>` でセル(列)のセクションを開始する(その行のプレースホルダ一覧内での位置が列インデックスになる)。
  - セクション内の箇条書きは、インデント無しの `- **太字**` 行がタイトル(3階層目)、その下にインデントされた `- ` 行が詳細(4階層目、直前のタイトルの子として連続する限り追加)。`**...**` はタイトルの装飾記法であり、生成される `OutlineNode.text` には含めない(太字かどうかは階層の深さで決まるため、テキストに書式を埋め込む必要がない)。
  - テーブルが無い、見出しがどの行/セルとも一致しない、箇条書きの行がどの `###` セクションにも属さない、といった形が崩れた入力は例外を投げず単に無視する(`outlineParser.ts` の「解釈できない行は無視」という既存方針を踏襲)。
- **図形の構成**(`bulletMatrix.ts`):
  - **行見出しセル**: 見出し付き箇条書きと同じ役割・同じ1図形構成だが、塗り色をテーマの `accent` にして列見出しと視覚的に区別する。
  - **列見出しセル**: 各列の上部に1つずつ(`columnHeaders` から直接生成、対応する `OutlineNode` を持たないため `templateNodeIds` は空)。塗り色は行見出しとは異なる `primary` 階調を使う。
  - **タイトル行・詳細行**: 見出し付き箇条書きの箇条書き項目と同様、枠なし・左揃えの `TextShape`(`bulletMarker` で表示専用の記号を付与)。タイトルは太字+下線(`ShapeStyle.fontWeight`/`textDecoration`)、詳細はタイトルよりやや薄い色・小さいフォントで、視覚的な階層を表す。
  - **グリッド線**: 行の間の横線(見出し付き箇条書きと同じ)に加え、列の間(行見出し列とセル列0の間を含む)にも縦線を引く。表の右端・上端(列見出しの上)・下端には線を引かない。
- **列数の増減**(`updateBulletMatrixColumns`): 列を追加すると既存の全行に新しい空セルが追加され、列を削除すると対応する列インデックスのセル(とその配下のタイトル・詳細)が全行から破棄される。既存の列がインデックスを保ったまま生き残る限り、その内容(タイトル・詳細)は保持される。
- マトリクス・ベン図・見出し付き箇条書きと同様、列数・行の箇条書き件数いずれの変更も全体を再レイアウトする(`isFullyRelayoutedPattern`)。テキストのみの編集(タイトル・詳細の文言変更)は位置に影響しないため、他パターンと同じ通常の同期(内容のみ更新)で扱う。

#### 6.2.5 ピラミッド図

見出し付き箇条書き(§6.2.3)の行見出しセルを、三角形を横に分割したピラミッドの各段(台形、最上段のみ三角形)に置き換えたもの。行見出しの右側に、箇条書きマトリクス(§6.2.4)と同様の複数列テーブルが続く。「ピラミッドストラクチャー」(6.2 冒頭の表、`pyramid.ts`)が階層テキストをそのまま木構造として解釈するのに対し、ピラミッド図は箇条書きマトリクスと同じ「階層2、位置ベース」の解釈規則を使う別パターン。

- **階層テキストは2階層**: 1階層目のノードがピラミッドの1段(出現順に最上段→最下段)、2階層目はその段の子で、**位置**により役割が決まる(テキスト自体は使わない位置もある点は箇条書きマトリクスのセルと同様)。子[0] は段の中(項目名の下)に表示する「(規模)」ラベル、子[1..] は `params.columnHeaders`(箇条書きマトリクスと同じ形、列見出しは階層テキストで表現しない)と位置対応するテーブルセル(単一テキスト、折り返しなし)。
- **図形の構成**(`pyramidChart.ts`):
  - **ピラミッドの段**: 新しい図形種別 `PolygonShape`(§3.1)の台形(最上段のみ頂点が一致する三角形)。段の総数 `n` のうち `i` 段目(0始まり、最上段が0)は、上辺の半幅が `i/n`、下辺の半幅が `(i+1)/n`(いずれもピラミッド全体の半幅に対する比率)の台形で、段を積み重ねると滑らかな三角形になる。塗り色はテーマの `primary` 階調を段ごとに変え(最上段が最も濃い `primary[0]`)、5段目以降は `primary[4]` に固定する。
  - **項目名・(規模)ラベル**: 段の図形の上に重ねて描く枠なしテキスト(見出し付き箇条書きの箇条書き項目と同様、`kind: "label"`)。段自体は文字を持たない背景専用の図形(`matrix.ts` の象限背景と同じ理由で、項目名/規模ラベルと別図形にする)。文字色は自身が乗る段の塗り色(上記)に対するコントラストで決める(`style.ts` の `contrastTextColor`、WCAG の相対輝度が閾値未満なら白、それ以外はテーマの通常の濃色)。段は最上段(`primary[0]`、濃色)から最下段側(`primary[4]`、淡色)へ変化するため、色を固定してしまうと濃い段では文字が沈み、淡い段では逆に白文字が沈む。`treeLayout.ts` の `contrastBgColorSlot`(自身が乗る段の `fillColorSlot` をそのまま渡す)経由で `sync.ts` の `styleFor` に伝える。
  - **テーブルセル**: 箇条書きマトリクスのセルと同様、列ごとに1つの枠なしテキスト(中央揃え)。
  - **タイトル・列見出し**: 全体の見出し(`params.title`、任意)をピラミッド段の左端から表全体の右端まで幅いっぱいに中央揃えで表示し、その直下に列見出し行との間を区切る実線(破線ではない)を1本引く。列見出し自体は箇条書きマトリクスと同じくテキストの下線装飾のみで、セル1つ分の罫線は引かない。
  - **行区切り線**: 見出し付き箇条書きと同様、段と段の間にのみ破線を1本引く(テーブル領域のみ、ピラミッド列は各段の塗り色が異なるため区切り線を要しない)。
- マトリクス・ベン図・見出し付き箇条書き・箇条書きマトリクスと同様、階層テキストの追加・削除は全体を再レイアウトする(`isFullyRelayoutedPattern`)。加えて、段の並べ替え(`moveOutlineNode` の↑↓、および字下げ/字上げ)も同様に全体を再生成する(`relayoutOrRegenerate`, `sync.ts`)。**理由**: 段の台形形状(上記の `i/n` 比率)は段の**位置**に依存するため、位置だけをコピーする通常の並べ替え処理(`relayoutBlock`)では並べ替え後も古い台形形状のまま取り残されてしまう。他パターンの図形はどれも自身の内容にのみ依存し位置に依存しないため、この問題はピラミッド図固有。
- テキストのみの編集(項目名・規模・セルの文言変更)は位置に影響しないため、他パターンと同じ通常の同期(内容のみ更新)で扱う。

#### 6.2.6 スケジュール

コンサル資料でよく使う、月次のガントチャート形式のスケジュール表(要求仕様3.2「ガントチャート」に対応。当初は「専用エディタ(将来)」としていたが、他パターンと同じ構造化テンプレートの枠組みで実現できると判断しMVPに組み込んだ)。年・月ヘッダー、マイルストーン(▼マーカー)、行ラベル、日付ベースで配置されるバー、バー間の依存線を1つのブロックとして生成する。

- **階層テキストは2階層+位置ベースの孫ノード**: 1階層目のノードが表の1行(出現順に上から配置)、2階層目はその行のバー(自由に追加・削除・並べ替え可能、バーの順序自体は描画に影響しない)。バーの3階層目([0]=開始日、[1]=終了日、いずれも `YYYY-MM-DD` の文字列)はピラミッド図の子ノードと同じ位置ベースの解釈規則だが、ラベルの自由入力ではなく `StructuredTextPanel.tsx` 側で専用の日付入力(`<input type="date">`)を出す。開始日・終了日のどちらかが未入力/不正な形式の場合、そのバーは(データとしては存在するが)描画をスキップする(他パターンの「不正データは無視」という既存方針を踏襲)。
- **月の範囲・マイルストーン・依存線は階層テキストで表現しない**: いずれも行/バーのような自然な木構造上の位置を持たないため(月範囲は表全体に1つ、マイルストーンはどのバーにも属さない、依存線は任意のバー同士を指す)、箇条書きマトリクスの列見出しと同じ理由で `StructuredBlock.params` の専用フィールドに持つ。
  - `params.startYear` / `startMonth` / `columnCount`: 表示する年・開始月・列(月)数。`StructuredTextPanel.tsx` に専用の数値入力を3つ設ける。
  - `params.milestones: { date: string; label: string }[]`: マイルストーンの一覧(日付+ラベル)。箇条書きマトリクスの列見出し入力と同様の可変長リストUI。表示テキストは `ラベル(M/D)` の形式で固定し(`schedule.ts` の `formatMonthDay`、ゼロ埋めなしの「6/29」表記)、日付をラベルに手入力させない。
  - `params.connections: Record<string, string>`: バーの依存線(`fromバーのnodeId -> toバーのnodeId` のフラットな対応表)。バーは行をまたいで自由に接続できるため親子関係では表現できず、`StructuredTextPanel.tsx` は各バーの行に接続先を選ぶ `<select>`(表示名は「行ラベル > バーラベル」、ドキュメント全体のバー一覧から選ぶ)を出す。
- **日付→座標変換**(`schedule.ts` の `dateToGridX`): 月内の日数(`daysInMonth`)を使い、月の何日目かを月内の比率に変換した上で `月インデックス + 比率` を列幅倍する。範囲外の日付はクランプせずそのまま(グリッド外に)描画する(誤入力に気づきやすいことを優先し、後述のツリー図/ロジックツリーのような黙示のクランプは行わない)。
- **図形の構成**(`schedule.ts`):
  - **年・月ヘッダー**: 行/バー領域の上に、年ラベル(表全体の月列幅いっぱい)+月ごとのセルを配置。塗り色は他パターンのような着色見出しではなく通常の `defaultShapeStyle`(白背景+紺の枠)とし、添付イメージの素朴な表ヘッダーの見た目に合わせる。
  - **行番号・行ラベル**: 行ごとに「(1)」等の連番セル(`(${index+1})`、階層テキストのノードではなく行の出現順から自動採番)と、行ラベルのセルを別図形として並べる(箇条書きマトリクスの行見出しと異なり着色しない)。
  - **バー**: `defaultShapeStyle` のテキスト付き矩形(添付イメージの淡い塗り+紺枠に合致)。開始日〜終了日の日付レンジをそのまま x 座標・幅に変換する(行内の縦位置・高さは固定)。
  - **マイルストーン**: 下向き三角形(`PolygonShape`、`headingStyle` のスロット0で濃色塗り)+ラベルのみ(グリッド最下段まで伸びる縦の目安線は持たない - 当初描画していたが、視覚的なノイズになるだけとのフィードバックにより削除した)。ラベルは三角形の直上(数px の隙間のみ)に配置する。月ヘッダーからの距離を固定の余白定数で確保するのではなく、三角形とラベル自身の高さの合計から「マイルストーン領域」の高さを逆算しているため、月ヘッダーへの食い込みが起きない(修正前は固定の余白定数を使っていたためラベルが浮いてカレンダーに重なる不具合があった)。
  - **グリッド線**: 月境界ごとの縦線(破線、箇条書きマトリクスと同じ扱い)、行の間の横線(破線、見出し付き箇条書きと同じ扱い)。
  - **依存線**(`params.connections`): 厳密なルーティングより見やすさを優先した簡略表示(「順序は行の上から下に流れる」という前提を置く)。同じ行同士(y が同じ)なら、バーAの右辺中央からバーBの左辺中央への矢印1本(`ConnectorShape`、`type: "arrow"`、矢印マーカー付き)。行をまたぐ場合は、バーAの右辺中央から右へ固定幅の短いスタブ(`CONNECTOR_STUB`、対象バーの開始位置の方が右にある場合はそちらを優先し、いずれにせよ最小限の右伸ばしのみ)を引いた後、下向きの矢印1本でバーBの上辺へ接続する、という2本構成のみ(水平のスタブ自体には矢印を付けない)。バーBの**開始位置に正確に接続するとは限らない**が、バーの最小幅(`BAR_MIN_WIDTH`)より `CONNECTOR_STUB` を十分小さくしてあるため、通常はバーBの上辺のどこかに着地する(この程度の誤差は許容する設計判断)。存在しないバーを指す依存(バー削除後に残った古い参照等)は描画時に無視する。矢印用に `treeLayout.ts` の `LayoutNode` へ `arrowhead` フラグを追加し、`true` のとき `sync.ts` の `regenerateBlockShapes` が(`LineShape` ではなく)`points` 付きの `ConnectorShape`(`fromShapeId`/`toShapeId` は付けない静的な矢印)を生成するようにした - `ConnectorRenderer.tsx`/EMF書き出し(`shape_draw.rs`)は既存の矢印描画をそのまま再利用できる。
- マトリクス・ベン図・見出し付き箇条書き・箇条書きマトリクス・ピラミッド図と同様、階層テキストの追加・削除は全体を再レイアウトする(`isFullyRelayoutedPattern`)。行の並べ替え(`moveOutlineNode` の↑↓、および字下げ/字上げ)もピラミッド図と同じ理由(ヘッダー・グリッド線・マイルストーン・依存線がいずれも特定のノードに紐付かない非追跡図形で、並べ替え後に取り残されてしまう)で全体を再生成する(`relayoutOrRegenerate`)。
- **テキスト編集の扱いが他パターンと異なる**: 行ラベル・バーラベルの文言変更は他パターン同様「該当図形の内容のみ更新」で済むが、開始日・終了日の変更は特別扱いする(`updateOutlineNodeText`/`sync.ts`)。日付ノード自体には対応する図形が存在しない(値そのものがバーの描画有無・位置・幅を決めるデータのため)ので、「一致する図形を探して内容を更新する」という他パターンの既定処理では何も起きない。そのためベン図と同様、スケジュールの階層テキスト編集は常に全体を再生成する。

#### 6.2.7 フロー図（縦型）

採用フロー等でよく使う、上から下へ流れる縦型のステップ図(添付イメージ: 「カジュアル面談」→「書類選考」→「選考面接」→…と、各段に色付きバッジ("STEP 0" 等)・タイトル・説明文を持ち、段の間を破線の矢印でつなぐもの)。ピラミッド図(§6.2.5)と同じ「階層2、位置ベース」の解釈規則を使う。

- **階層テキストは2階層、位置ベース**: 1階層目のノードが1つのステップ(出現順に上から配置)、2階層目は子[0]=バッジラベル(例: "STEP 0"、"JOIN !!")、子[1..]=タイトル下に並べる説明文の各行(折り返しを行わない他パターンと同じ制約のため、1文を1行として複数ノードに分けて入力する)。バッジラベルをステップの出現順から自動採番しない(`0, 1, 2...`)理由: 添付イメージの最終段が "STEP 4" ではなく "JOIN !!" のように、実務では命名パターンが最後だけ崩れることが普通にあるため。
- **図形の構成**(`verticalFlow.ts`):
  - **バッジ**: 見出し付き箇条書きの見出しセルと同じ塗り+ラベル一体の図形(`kind: "heading"`)。塗り色はテーマの `primary` 階調を段ごとに変え(先頭が最も薄い `primary[4]`、後になるほど `primary[0]` へ濃くなる)、**最終段のみ `accent`** にする(添付イメージの最終段 "JOIN !!" が他と異なる色調で描かれているのに合わせた特別扱い)。ラベル文字色は `treeLayout.ts` の `contrastBgColorSlot`(自身の `fillColorSlot` をそのまま渡す)経由でコントラスト計算するため、薄い段でも濃い段でも読める(ピラミッド図の項目名ラベルと同じ理由、§6.2.5)。
  - **タイトル**: バッジの右に太字で描く枠なしラベル(`kind: "label"`)。バッジと共通の「ヘッダー帯」の高さの中で垂直方向に中央揃えする。
  - **説明文**: タイトルの直下に、子[1..] の件数ぶん1行ずつ積む枠なしラベル。タイトルよりやや薄い色(`textColorSlot`)・小さいフォントで、視覚的な階層を表す(ピラミッド図のタイトル/詳細と同様の考え方)。
  - **矢印**: 隣接する段のバッジ同士を、上の段の下辺中央から下の段の上辺中央へ破線の矢印(`arrowhead: true`)でつなぐ(スケジュールの依存線と同じ、`treeLayout.ts` の `arrowhead` フラグ経由で `ConnectorShape` を生成)。対応する `OutlineNode` を持たない非追跡図形(`nodeIds: []`)。
- ピラミッド図・スケジュールと同様、階層テキストの追加・削除は全体を再レイアウトする(`isFullyRelayoutedPattern`)。段の並べ替え(`moveOutlineNode` の↑↓、および字下げ/字上げ)もスケジュールと同じ理由(矢印が非追跡図形で、並べ替え後に取り残されてしまう)で全体を再生成する(`relayoutOrRegenerate`)。
- バッジ(子[0])はピラミッド図の位置ベースの子と同様、`StructuredTextPanel.tsx` 上で並べ替え・字下げ/字上げ・削除・子の追加を無効化する(常に子[0]に存在する前提でレイアウト関数が読むため)。説明文(子[1..])はこの制約を受けず、通常のノードと同じく自由に追加・削除・並べ替えできる。
- テキストのみの編集(バッジ・タイトル・説明文の文言変更)は位置に影響しないため、他パターンと同じ通常の同期(内容のみ更新)で扱う。

#### 6.2.8 フロー図（横型）

採用フロー等でよく使う、左から右へ流れる横型のステップ図(添付イメージ: 円形の各段(「カジュアル面談」→「応募/書類選考」→「面接」→…)を矢印でつなぎ、先頭の段だけ点線円(任意参加を示す)、以降の段は塗りつぶし円(段が進むごとに色が濃くなる)で描くもの)。

- **階層テキストは1階層+任意の追加行**: 1階層目のノードが1つのステップ(出現順に左から配置)で、**そのノード自身のテキストが円に表示されるメインのラベル**(=「親文字列だけを入力すればそれがそのまま表示される」)。子(`+子` で追加、任意)はそのステップのラベルをもう1行増やしたい場合の追加行で、位置ベースではない普通のノードとして扱う(フロー図(縦型)のバッジ(§6.2.7)やピラミッド図の子のような固定位置の特別な子ではない - ステップが1行で完結する場合は子を追加する必要が一切ない)。折り返しを行わない他パターンの制約により、2行に分けたいラベル(添付イメージの「応募」「書類選考」等)はルート+子1件の2ノードとして入力する。
- **図形の構成**(`horizontalFlow.ts`):
  - **円**: `kind: "ellipse"` に新たに対応した塗りつぶし(`fillColorSlot` 指定時、`style.ts` の `filledShapeStyle`)。**先頭の段(出現順で最初のルート)のみ、`fillColorSlot` を指定せず、かつ破線(`dashed: true`)にする**ことで、添付イメージの「任意参加」を示す点線・塗りなしの円を表現する(バッジ色を最終段だけ `accent` にするフロー図(縦型)とは逆に、こちらは**先頭**の段だけ特別扱いする)。2段目以降は塗りつぶしで、段が進むほど `primary` 階調が濃くなる(フロー図(縦型)の `badgeColorSlot` と同じ考え方だが、最終段の `accent` 予約はない - 添付イメージが最後まで単調に濃くなるだけで、縦型のような別種のゴールを示す色分けをしていないため)。円は楕円としての新しい図形であり、venn.ts の集合円と同様それ自体はテキストを持たず、ラベル行は別図形として上に重ねる(`kind: "label"`)。
  - **ラベル行**: ルート自身のテキスト+その子の件数ぶんを、円の中央にすべて同じ太字スタイルで縦積みし、ブロック全体を円の中央に来るよう配置する。文字色は円が塗りつぶしの場合 `contrastBgColorSlot`(自身の円の `fillColorSlot` を渡す)でコントラストを自動選択し(フロー図(縦型)のバッジラベルと同じ理由)、先頭段(塗りなし)は指定せず通常の濃色文字にする。
  - **矢印**: 隣接する円同士を、右の円の右辺中央から左の円の左辺中央へ実線の矢印(`arrowhead: true`、`dashed: false`)でつなぐ(フロー図(縦型)の破線矢印と異なり、添付イメージに合わせて実線)。対応する `OutlineNode` を持たない非追跡図形(`nodeIds: []`)。
- **`kind: "ellipse"`/`"rect"` への塗りつぶし対応**(`treeLayout.ts`/`sync.ts`): これまで `ellipse`/`rect` は常に塗りなしの輪郭(`outlineStyle`)だったが、`LayoutNode.fillColorSlot` を指定した場合は塗りつぶし(`filledShapeStyle`、テキストを持たないため `headingStyle` とは別の軽量な関数)に、`LayoutNode.dashed: true` を指定した場合は破線の輪郭(`outlineStyle` の第2引数)になるよう拡張した。`line` の `dashed` (未指定 = 破線)とは既定値の向きが逆(`ellipse`/`rect` は未指定 = 実線)である点に注意。
- フロー図(縦型)と同様、階層テキストの追加・削除は全体を再レイアウトする(`isFullyRelayoutedPattern`)。段の並べ替え(`moveOutlineNode` の↑↓、および字下げ/字上げ)も全体を再生成する(`relayoutOrRegenerate`)- フロー図(縦型)と同じ「矢印が非追跡図形」という理由に加え、**円自身の塗り/破線が自身の位置(出現順インデックス)に依存する**ため(ピラミッド図の台形の傾きと同じ理由)、位置だけをコピーする通常の並べ替え処理では並べ替え後も古い色・線種のまま取り残されてしまう。
- テキストのみの編集(ラベル行の文言変更)は位置に影響しないため、他パターンと同じ通常の同期(内容のみ更新)で扱う。

#### 6.2.9 フロースケジュール（縦）

問い合わせ〜利用開始のような対応の流れを、番号付きの見出しセル+説明文の行として上から下へ並べる図(添付イメージ: 「フロースケジュール（縦）」という見出しを左右の破線で挟んだタイトル行の下に、「01｜お問い合わせ」「02｜ヒアリング」…と連番付きの色付き見出しセルが並び、その右に各行の説明文が続く。行の間は破線で区切る)。見出し付き箇条書き(§6.2.3)に「見出しの連番」と「全体タイトル」を足したもの。

- **階層テキストは1階層+任意の子**: 1階層目のノードが1つの行(出現順に上から配置)で、そのノード自身のテキストが見出しセルのラベル(先頭の "01 | " 等は出現順から自動生成し、階層テキストには含めない)。子(`+子` で追加、任意・個数制限なし)はその行の説明文で、見出し付き箇条書きの箇条書き項目と異なり「• 」等のマーカーは付けない(添付イメージの説明列が素のテキストであるため)。行・子とも位置ベースではない普通のノードとして扱われ、フロー図(縦型)のバッジ(§6.2.7)のような固定位置の特別な子は存在しない。
- **全体タイトルは階層テキストで表現しない**: ピラミッド図の `params.title`(§6.2.5)と同じ理由(行のような自然な木構造上の位置を持たない)で `params.title`(任意)に持ち、`StructuredTextPanel.tsx` に同じ単一テキスト入力(`PyramidChartTitleInput` を両パターンで共用)を出す。
- **図形の構成**(`flowSchedule.ts`):
  - **見出しセル**: 見出し付き箇条書きの見出しセルと同じ塗り+ラベル一体の図形(`kind: "heading"`、塗り色は全行共通でテーマの `primary[0]`、段ごとの色分けはしない)。連番("01 | " 等、`rowNumberPrefix`)は `TextShape.bulletMarker`(§3.1、見出し付き箇条書き/箇条書きマトリクスの "• "/"- " と同じ仕組み)経由でラベルの前に描画専用で付加し、ノードの実テキスト(`row.text`)には含めない。こうすることで連番は出現順インデックスから毎回導出される一方、見出しラベルの文言編集は他パターンと同じ「対応する図形の `content` のみ更新」という既定の同期(`updateOutlineNodeText`)でそのまま扱え、スケジュール(§6.2.6)の日付フィールドのような特別扱いが不要になる。
  - **説明文**: 見出しセルの右側に、子の件数ぶん1行ずつ積む枠なしラベル(`kind: "label"`、マーカーなし)。子が複数件のときは行の高さの中で縦方向中央揃えのブロックとして配置する(見出し付き箇条書きの箇条書き項目が上詰めなのに対し、添付イメージの説明列が1行だけでも行の中央に来ている見た目に合わせた)。
  - **タイトル**: `params.title` が空でなければ、全体(見出しセル+説明列)の横幅の中央に太字・`accent` 色のラベル(`kind: "label"`)を配置し、その左右をタイトル帯の外側まで破線(`kind: "line"`、既定の破線)で埋める(添付イメージの「フロースケジュール（縦）」を挟む左右の破線)。ピラミッド図のタイトル(見出しの上に全幅の実線区切りを1本引くだけ)とは異なる専用の見た目のため、ピラミッド図の `layoutPyramidChart` とは別に `layoutFlowSchedule` 内で完結させている。
  - **行区切り線**: 見出し付き箇条書きと同様、行と行の間にのみ破線を1本引く(説明列のみ、見出し列は全行同色のため区切り線を要しない)。
- 見出し付き箇条書き・ピラミッド図・スケジュール・フロー図(縦型/横型)と同様、階層テキストの追加・削除は全体を再レイアウトする(`isFullyRelayoutedPattern`)。行の並べ替え(`moveOutlineNode` の↑↓、および字下げ/字上げ)も全体を再生成する(`relayoutOrRegenerate`)- フロー図(横型)と同じ「非追跡図形(タイトル・行区切り線)と、自身の位置(出現順インデックス)に依存する見た目(見出しセルの連番)の両方を持つ」という理由による。
- テキストのみの編集(見出しラベル・説明文の文言変更、タイトルの変更)は位置に影響しないため、他パターンと同じ通常の同期(内容のみ更新、タイトルは `updateFlowScheduleTitle` 経由でピラミッド図の `updatePyramidChartTitle` と同様に全体再生成)で扱う。

### 6.3 双方向同期

- 同期の単位は「テキストのラベル内容」のみ(要求仕様 4.2 の方針どおり、配置・サイズ・色は同期しない。ベン図の所属集合変化時の位置再計算のみ §6.2.2 の例外)。
- アウトライン側の `OutlineNode`(`nodeId`)と、生成された `TextShape.content`(または図形のラベル)を `templateNodeIds` で対応付ける(通常1対1。ベン図の共有要素のみ多対1、§6.2.2)。
  - アウトライン側で行のテキストを編集 → 対応する `nodeId` を含む図形の `content` を更新(図形の位置・サイズは変更しない)。
  - 図形側でラベルを直接編集 → 対応する `nodeId` の行テキストを更新。
- ノードの追加・削除は、§6.1 のとおり構造化アウトラインエディタ上の明示的な操作(`addSibling` / `addChild` / `deleteNode`)として行われるため、diffは不要で以下のルールをそのまま適用できる。
  - 子ノードの追加: 親ノードに対応する図形の近傍(右下に固定オフセット)へデフォルトサイズで新規図形を生成する。
  - ルート(親を持たない)ノードの追加: 同ブロック内の既存の最後のルート図形を基準に、ピラミッドは下方向、ロジックツリーは右方向へ固定オフセットで配置する。既存ルートが1件もない場合はブロックの基準位置(ブロック初期配置位置)に配置する。マトリクス/ベン図でのルート追加上限は §6.2.1 / §6.2.2 のとおり。
  - 削除時は対応図形を削除する。
  - いずれも Undo 可能なため確認ダイアログは出さない。
- 図形側での図形自体の追加・削除(テンプレート生成後に自由配置キャンバス上で行う操作)は、要求仕様どおりアウトライン側にフィードバックしない(`templateNodeIds` を持たない通常図形として扱われる)。

### 6.4 ユーザーテンプレート登録

要求仕様 4.4「よく使う図形の組み合わせをユーザー自身がテンプレート登録できる」に対応する。構造化テンプレート(6.1〜6.3、階層テキストからの自動生成)とは独立した機能で、テキストとの同期は行わない。

- 登録操作: キャンバス上で1つ以上の図形を選択した状態で「テンプレートとして登録」を実行する(`PropertyPanel.tsx` のツールバーまたは選択図形の右クリックメニュー)。選択図形群をバウンディングボックス左上原点の相対座標に正規化して `UserTemplate`(§3.4)として保存する。
- 保存先: プロジェクトファイルではなく、プロジェクトを跨いで再利用できるようアプリ設定ディレクトリに `user_templates.json` として保存する(`recent_files.rs` と同様の方式、`user_templates.rs` が読み書きを担う)。
- 配置: `TemplateLibraryPanel.tsx` の「マイテンプレート」タブから選択・配置する。配置時は `shapes` を新規 `ShapeId` で複製し、ドロップ位置を基準に絶対座標へ変換した上で通常図形としてドキュメントに追加する(`templateNodeIds` は付与しない)。
- 削除: マイテンプレート一覧から削除操作を行う(`user_templates.rs` 側の該当エントリを削除)。

## 7. スタイル・配色プリセット

- 配色テーマは `ColorTheme { id, name, primary[5], accent, textDark, textLight }` の形で3プリセットを標準搭載する。
  1. **Neutral Blue**: 紺・グレー基調(標準的なコンサル資料トーン)
  2. **Warm Gray**: ベージュ・ブラウン基調
  3. **Monochrome**: グレースケール+アクセント1色
- 各プリセットの正確な HEX 値は実装時に確定してよい(要求仕様と矛盾しない実装細部のため)。
- テーマ切り替え(`Document.colorThemeId` の変更)は、以後 `createShape` で新規作成する図形の初期 `style` にのみ反映される。既存図形の `style` は各図形に個別の値として保持されており、テーマ切り替えでは遡って変更しない(要求仕様 4.3 で明確化)。スタイルパネルのクイックスウォッチ(現在のテーマの色をワンクリックで適用)は、既存図形に配色を反映させたい場合の手動手段として提供する。
- 「書式のコピペ」は選択図形の `style` オブジェクトをクリップボード的な一時状態(`selectionStore` 内)に保持し、貼り付け先図形の `style` を上書きする形で実装する。

## 8. 出力・エクスポート

### 8.1 SVG エクスポート

- フロントエンドで `Document` から SVG 文字列を組み立て(キャンバス描画と同じロジックを再利用)、Tauri の `project.rs` 経由でファイル書き込みのみバックエンドに委譲する。

### 8.2 PNG エクスポート

- Rust 側で **resvg** クレートを用い、フロントエンドが渡す SVG 文字列を指定解像度でラスタライズして PNG を生成する。日本語フォントの埋め込み・解像度指定の確実性を優先し、フロントエンド側の `<canvas>` 変換ではなくバックエンドでの処理とする。

### 8.3 PowerPoint 貼り付け対応(EMF)

事前調査の結果、Rust エコシステムには SVG やベクターモデルから EMF を直接生成できる十分にメンテナンスされたクレートは存在しない(`emf-core` 等は EMF→SVG の逆方向変換のみ対応)。そのため以下の方式を採る。

- **方式**: Rust バックエンドが Shape モデル(JSON、resvg には渡さず独自変換)を解釈し、`windows-rs` クレート経由で Win32 GDI の `CreateEnhMetaFile` によるメタファイル記録用 DC を作成、`Rectangle` / `Ellipse` / `Polygon` / `PolyBezier` / `MoveToEx`+`LineTo` / `TextOutW` などの GDI 描画命令を Shape ごとに発行し、`CloseEnhMetaFile` で `HENHMETAFILE` を得る。
  - SVG パーサを経由しないため、対応図形セット(矩形・楕円・多角形・直線・矢印・コネクタ・テキスト)の範囲では変換の忠実性が高い。`PolygonShape`(§3.1、ピラミッド図の段 - §6.2.5)は `points`(比率)を Shape の x/y/width/height で絶対座標へ変換してから `Polygon` に渡す(`emf/shape_draw.rs`)。
- **ファイルへのエクスポート**: `CopyEnhMetaFile` で `.emf` ファイルとして複製保存する。
- **クリップボード経由の PowerPoint 貼り付け**: `OpenClipboard` → `EmptyClipboard` → `SetClipboardData(CF_ENHMETAFILE, handle)` → `CloseClipboard` を Win32 API 直呼び(`windows-rs`)で実装する。`clipboard-win` クレートは `CF_ENHMETAFILE` 定数を提供しているため、低レベル API のラッパーとして利用を検討する。
- **フォールバック(MVPでの簡略化)**: 設計時点ではGDI失敗時にPNGのクリップボード転送へ自動フォールバックする方針としていたが、実装時にCF_DIB形式でのビットマップ合成・クリップボード書き込みを新たに実装するコストに対して優先度が低いと判断し、MVPでは見送った。GDI生成/クリップボード転送に失敗した場合は、エラー内容をユーザーに通知し「PNG画像としてのエクスポートをお試しください」という案内を表示するに留める(自動フォールバックはしない、ユーザーが手動でPNGエクスポートをやり直す)。
- Tauri 公式クリップボード API はテキスト/HTML までしか対応しておらず画像系カスタムフォーマットに未対応のため、この処理は自作の Tauri コマンド(`export_emf.rs` / `clipboard.rs`)として実装し、既存のクリップボードプラグインには依存しない。
- **既知のリスク**: SVG/PNG(§8.1, 8.2)はフロントエンドのSVG描画ロジックを再利用する一方、EMF(本節)はRust側でShapeモデルから独立してGDI描画命令を組み立てる、完全に別の描画パイプラインになる。フォントレンダリングや矢印形状の丸め等で両者の見た目が将来的に乖離するリスクがあるため、対応図形を追加・変更する際は両方のレンダラを同時に確認する運用ルールとする。
- **既知の制限事項(テキスト揃え)**: 生成したEMFを`PlayEnhMetaFile`で直接再生した場合(`src-tauri/examples/emf_align_debug.rs`で検証可能)、`SetTextAlign`による左/中央/右揃えは正しく描画される。しかし、PowerPointに貼り付けた図形を「グループ化解除」して個別図形(PowerPoint独自のテキストボックス形式)に変換すると、揃え情報が引き継がれず左揃えに正規化される事象を確認した。`TextOutW`+`SetTextAlign`というGDIの描画命令列を、PowerPoint固有のテキストボックスオブジェクトへ変換する処理自体の仕様に起因すると考えられ、GDI側の描画命令をこれ以上調整しても解決しない。グループ解除せずに画像として扱う分には正しく表示される。MVPでは対応を見送り、既知の制限として記録する。

## 9. プロジェクト管理

- 直近使用ファイル一覧は Tauri のアプリ設定ディレクトリ(`app_config_dir()`)に `recent_files.json` として保存し、`recent_files.rs` が読み書きを担う(最大件数はさしあたり10件)。
- 新規作成・開く・保存・名前を付けて保存は `commands/project.rs` の Tauri コマンド(`project_new` は実質フロントエンド側で空 `Document` を生成するのみ、`project_open`/`project_save`/`project_save_as` はファイルダイアログ+I/O)として実装する。
- ユーザーテンプレート(§3.4, §6.4)は同様にアプリ設定ディレクトリに `user_templates.json` として保存し、`user_templates.rs` が読み書きを担う。

## 11. エラーハンドリング方針

- Rust 側は `thiserror` で `AppError` を定義し、`io::Error` / GDI 呼び出し失敗 / シリアライズ失敗などを列挙型のバリアントに変換して IPC 境界でメッセージ化する。生の OS エラーコードをそのままユーザーに見せず、`kind` ごとにフロントエンド側で日本語メッセージへマッピングする。
- フロントエンドは Tauri コマンド呼び出しを共通ラッパー(`tauriApi.ts`)経由で行い、失敗時はトースト通知で表示する。ファイル保存/エクスポート系の失敗はキャンバスの状態(Undo履歴含む)に影響を与えない(失敗してもアプリ内状態はロールバックしない = そもそも状態を変更する前に実行する)。
- 階層テキストのパースはエラーを許容する設計にする(不正な行は無視して処理を継続し、パース不能で図形が1つも生成できない場合のみ「入力を確認してください」という非破壊的な警告を表示する)。テンプレート生成に失敗しても既存図形は保持される。

## 12. パフォーマンス方針

- 要求仕様どおり MVP では具体的な数値目標を定めない。
- 数十〜百オブジェクト規模であれば SVG 直接操作でも実用的な速度が出る想定(仮想化やCanvas化は将来のパフォーマンス検証フェーズで検討)。
- **設計と実装の差異**: 当初「Zustandストアの購読粒度を図形単位(`useShape(id)`のようなセレクタ)にし、無関係な図形の再描画を避ける」という配慮を想定していたが、実装では`Canvas.tsx`は`document`オブジェクト全体を購読しており(図形1個の変更でも全図形が再評価される)、この最適化は行っていない。数十〜百オブジェクト規模のシンプルなSVG要素であればReactの再レンダリングコストは実用上問題にならないと判断し、MVPでは見送った。将来、体感的な速度低下が確認された場合に導入を検討する。

## 13. テスト方針

- フロントエンド: **Vitest** + React Testing Library。
  - `outlineParser.ts`/`outlineSerializer.ts`、`pyramid.ts`/`logicTree.ts`/`matrix.ts`/`venn.ts`、`snap.ts`/`align.ts`、`sync.ts` は UI から独立した純関数群として実装し、単体テストの主対象とする。
  - 境界値例: 空のアウトライン入力、ノード1個のみ、マトリクスで象限がUI制約を経由せず(手編集インポート等で)5個以上ある入力(`matrix.ts` が4個目までのみ図形化することを確認)、ベン図で3集合すべてに共通する要素、同一集合内の重複要素、ベン図で要素テキスト編集により所属集合の組み合わせが変化するケース(位置が再計算されることを確認)。
  - 構造化アウトラインエディタの `addSibling`/`addChild`/`indent`/`deleteNode` 操作それぞれについて、対応する `nodeId` の生成・破棄と図形への反映を検証する。
  - Undo/Redo: 複数操作→Undo連打→Redo連打で状態(スナップショット)が一致することを検証する。
  - ユーザーテンプレート: 複数図形選択→登録→座標正規化→別位置への配置で絶対座標へ正しく変換されることを検証する。
- バックエンド: `cargo test` で `project_file.rs` のシリアライズ/デシリアライズの往復一致、`shape_draw.rs` の Shape→GDI描画命令列への変換ロジック(GDI 呼び出し自体から分離した部分)を検証する。実際の GDI 呼び出し・クリップボード転送は Windows 実行環境に依存するため自動テスト対象外とし、後述の手動動作確認で担保する。
- E2E テストは MVP の対象外とする(手動動作確認で代替。将来的に Tauri 向け E2E ツールの導入を検討)。

## 14. パッケージング方針

- `src-tauri/Cargo.toml` と `package.json` それぞれにバージョンを持たせず、`tauri.conf.json` の `version` を単一の真実源とし、ビルド時に両ファイルへ反映するスクリプトを `package.json` の `scripts` に用意する。
- 主要な追加依存(候補): フロントエンド `zustand`, `immer`, `react-moveable`, `uuid`。バックエンド `windows-rs`(GDI呼び出し用), `resvg`, `serde`/`serde_json`, `thiserror`。`clipboard-win` はクリップボード書き込みの補助として採否を実装時に判断する。
